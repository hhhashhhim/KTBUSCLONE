## Confirmed defects

### QA 1 High priority account isolation failure — fixed in the working tree

**Original release blocker, now corrected locally.** Before the fix, signing out after loading account A's saved passengers and signing in as account B without killing the app could display account A's names and identification/contact details. Wallet balance, cached bookings and passenger details in the booking draft also survived the change. This was a local session-cache privacy defect; it did not establish that the server permits cross-account reads.

The original widget test rendered account A's saved-passenger name after switching to account B. Three provider/controller checks separately reproduced the stale wallet, stale bookings and retained draft. Tests use synthetic accounts and the real logout controller; no production data is involved.

Original cause: [saved-passenger, wallet and booking providers](../lib/features/travel/application/travel_providers.dart) persisted independently of passenger identity; [logout and expiry handling](../lib/features/auth/application/auth_controller.dart) cleared authentication without resetting those providers or the booking draft. Home read the booking cache directly. Refreshing My Trips did not resolve the other caches or the underlying exposure.

The fix scopes these private caches to each login session, resets the booking draft, rejects obsolete async results at affected update points, and removes private routes on expiry, logout, biometric lock and account switching. Same-account profile edits preserve the active session.

Verification: **24/24 isolation and navigation checks pass**, including the original four reproductions, pending and failed loads, delayed responses, logout, expiry, biometric lock, same-account re-login, profile editing and private-route removal. They now run in the default `test/` suite. The original command `flutter test --no-pub qa/account_isolation_test.dart` remains available through a wrapper. [Fix notes and evidence](ACCOUNT_ISOLATION_FIX_2026-10-26.md). No backend change or deployment was made.

### QA 2 Booking gender choice conflicts with the backend

The [passenger form](../lib/features/travel/presentation/lovable_search_flow.dart) offers `male`, `female` and `other` at line 1481. Its continuation path submits the selected value. `mobile-backend`'s `app/Http/Requests/Mobile/QuoteBookingRequest.php` accepts only `male,female`, and its passing `test_unsupported_booking_gender_returns_validation_error_without_creating_quote` explicitly verifies HTTP 422 for `other`.

A traveller can complete the form using a visible option and then be unable to obtain a fare quote. Saved passengers with this value have the same contract limitation. This was confirmed from the active Flutter code and executed backend acceptance test, not by sending a live booking request.

Required correction: explain the booking limitation before checkout and offer a support path. Do not silently change the passenger's gender. Supporting another value requires an agreed ERP representation and separate work on `mobile-backend`.

### QA 3 Large text overflows the bottom navigation

`test/seat_layout_test.dart` fails its large-text case at 375 × 812 with text scale 1.6. Four navigation items overflow by five pixels at [app_shell.dart](../lib/features/shell/app_shell.dart), line 189. The fixed-height bar does not leave enough space for the scaled labels. This is an accessibility/layout defect, reproduced in the full suite and isolated rerun.

Acceptance: navigation labels and buttons remain visible and usable at enlarged text sizes without RenderFlex exceptions, including while selecting seats.

### QA 4 Seat map no longer fits the existing standard-phone requirement

At 375 × 812 with top/bottom insets 44/34, the 42-seat test expects zero vertical scrolling but measures **13 logical pixels** of scroll extent. This is a layout regression against the existing acceptance test, not proof that a seat is unbookable; the map remains scrollable. The larger bottom navigation reduces available map space.

Acceptance: restore the agreed all-seats-visible layout on this size or explicitly revise the requirement after checking that the last row and Continue remain easy to reach. Do not merely remove the failing assertion.

## Release decision and remaining gates

Proceed with internal development and controlled QA. **Do not approve public release on this evidence.**

1. Account isolation correction is complete in the working tree: all four original reproductions and 20 additional checks pass. Include this source change in the next accepted build.
2. Resolve the booking gender mismatch and both layout failures. Rerun the affected tests and the full Flutter suite.
3. Decide which optional features belong in the release. Configure and accept wallet/push if included; make unavailable capabilities clear in the app if excluded.
4. Validate approved store identities, release signing, version policy and update links. Produce and validate actual release artifacts.
5. In a separately authorized test environment, complete signup → OTP → login → search → seats → passengers → quote → booking → payment or branch confirmation → confirmed ticket → My Trips. Include expired quotes, sold seats, duplicate taps, network loss and app restart.
6. Verify payment provider acceptance and reconciliation, real-device biometrics and push, MySQL expiry tests, and concurrent booking behavior. Keep self-service cancellation/refund/rescheduling and payment retry clearly outside the release unless separately implemented.
